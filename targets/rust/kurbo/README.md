# kurbo

[linebender/kurbo](https://github.com/linebender/kurbo).

## What is tested

**`src/affine.rs`**
- `affine_composition_associates_over_points`: The doc comment on `Affine::new` promises `(A * B) * v == A * (B * v)` — composition then application agrees with successive application. Generalizes the three fixed points of the `affine_mul` unit test to arbitrary matrices and points. The tolerance is scaled by the cube of the largest input magnitude, matching the double matrix-vector product's worst-case intermediate magnitude.
- `affine_inverse_composes_to_identity`: `inverse` documents NaN output only for zero determinant; for well-conditioned invertible transforms (built here from rotations, non-degenerate scales, and a translation) composing with the inverse must give back the identity map, up to floating-point error. Generalizes the single fixed matrix of the `affine_inv` unit test.

**`src/bezpath.rs`**
- `pathseg_eval_at_endpoints_matches_start_and_end`: `ParamCurve::start`/`end` document defaults of `eval(0.0)` and `eval(1.0)`; the specialized overrides on `Line`, `QuadBez` and `CubicBez` (which return the control points directly) must agree with `eval` at the endpoints to within a few ULPs — and in particular `eval` of an all-finite curve (`is_finite() == true`) at its endpoints must not be NaN or infinite. KNOWN FAILURE — real bug, kept failing deliberately; do not "fix" the test. Intermediate overflow makes `eval` return NaN or infinity at the endpoints of finite curves with extreme (but finite, `is_finite() == true`) coordinates: - `Line::eval` uses `lerp`, i.e. `p0 + t * (p1 - p0)`; when the   endpoint coordinates have opposite signs and magnitude above   ~9e307, `p1 - p0` overflows to infinity, so `eval(0.0)` is   `0.0 * inf = NaN` and `eval(1.0)` is infinite. Example:   `Line((0, -1.797e308), (0, 6.5e307))` has `eval(0.0) = (0, NaN)`. - `QuadBez::eval`/`CubicBez::eval` multiply interior control points   by 2 or 3 before scaling by `t`; for `|p1| > f64::MAX / 3`,   `eval(0.0)` evaluates `(p1 * 3) * 0 = inf * 0 = NaN`. Coordinates cover the whole finite range; the `sampled_from` branch boosts the extreme-magnitude region so the failure reproduces on every run. Sibling tolerance-based properties cap coordinates at ±1e9, which also keeps them clear of this bug.
- `pathseg_subsegment_matches_eval_reparameterization`: `subsegment(t0..t1)` is documented as "a subsegment of the curve for the given parameter range": evaluating the subsegment at `s` must match evaluating the original curve at `t0 + s * (t1 - t0)`. Generalizes the fixed-value `quadbez_subsegment` unit test to all three segment kinds and arbitrary ranges.
- `pathseg_arclen_between_chord_and_control_polygon`: The arc length of a Bézier segment lies between the chord length and the length of the control polygon (a standard consequence of the convex hull property), so `arclen` — documented as "accurate to the given accuracy" — must land between those bounds, give or take the accuracy plus rounding slack.
- `pathseg_bounding_box_encloses_curve_within_control_box`: `ParamCurveExtrema::bounding_box` is documented as "the smallest rectangle that encloses the curve in the range (0..1)". Check both directions: every sampled curve point lies inside the box, and the box lies inside the control-point bounding box (convex hull property).
- `pathseg_nearest_is_at_least_as_close_as_sampled_points`: `nearest` is documented as "the position on the curve that is nearest to the given point". Check the returned `Nearest` is internally consistent (`distance_sq` matches evaluating at `t`), that `t` lies in [0, 1], and that no sampled point on the curve is closer than the claimed nearest distance. The `accuracy` argument reaches polycool's `roots_between` as `x_error`, i.e. it is a tolerance on `t`, not on distance, so the distance slack is `accuracy` times a bound on the curve's speed (`|B'(t)| <= 3 * max control leg length`).
- `flatten_stays_within_tolerance`: `flatten` documents that the output is made of straight-line elements only, and that the polyline approximates the curve to within `tolerance` (Hausdorff distance). Sampling points on the source curve and measuring their distance to the emitted polyline is a lower bound on the Hausdorff distance, so it must stay within tolerance. The docs hedge that the bound is "not absolutely guaranteed", and indeed hairpin quads (endpoints nearly mirrored across the apex, e.g. `Q0,2 56.4,0 0,0` at tolerance 0.125) exceed it by ~7%, so this test allows 2x tolerance; the *unbounded* violations from degenerate quads are a separate pinned bug (see the exclusion below and `flatten_collapses_exactly_degenerate_quads`).
- `flatten_collapses_exactly_degenerate_quads`: KNOWN FAILURE — real bug, kept failing deliberately; do not "fix" the test. `flatten` collapses a quad whose parabola transform is exactly degenerate to a single line segment between its endpoints, at *any* tolerance, losing an arbitrarily large excursion. In `QuadBez::estimate_subdiv`, `cross = (p2 - p0).cross(d01 - d12)` is exactly 0 when the endpoints coincide (a "petal", regardless of where the control point is) or when the control points are exactly collinear and the curve retraces itself; `scale` is then NaN, `val` becomes 0, and a single segment is emitted. Concretely, flattening `M0,0 Q50,80 0,0` at tolerance 0.01 emits only `[MoveTo((0,0)), LineTo((0,0))]` even though the curve extends to (25, 40) — a Hausdorff error of ~47, unbounded in general (compare the doc's "attempts to bound this distance"). Exactly collinear retraced quads (e.g. `Q(0,3) 0,1` from the origin, apex error 0.75 at any tolerance) collapse the same way, cubics reach the same code path via `to_quads`, and there is an underflow variant: endpoints distinct but so close relative to the control excursion (chord below ~1e-244) that the internally computed `scale` underflows to 0. Every case generated here is an exact petal whose excursion exceeds the tolerance several times over, so this test fails deterministically on every run.

**`src/quadbez.rs`**
- `quadbez_arclen_of_point_quad_is_zero`: KNOWN FAILURE — real bug, kept failing deliberately; do not "fix" the test. `QuadBez::arclen` returns NaN for a point-degenerate quad (all three control points identical), where the correct arc length is 0. In the analytic formula both `a` (from `d2 == 0`) and `c` (from `d1 == 0`) are zero, so the nearly-straight fallback check `a < 5e-4 * c` fails, `a.powf(-0.5)` is infinite, and `ba_c2 = b * a2 + c2` is `0 * inf = NaN`. `Line::arclen` and `CubicBez::arclen` both return 0 for the analogous degenerate inputs, and `perimeter_not_nan` above (#477) shows NaN-freedom is intended. Point-degenerate quads occur in practice as the closing segment of paths whose pen position never moves. The same NaN also arises for any quad small enough that both squared control-point differences underflow to 0 (spread below ~1.5e-162), e.g. `QuadBez((0,0), (0,4.4e-302), (0,5e-324))`. Fails deterministically: every generated case is a point quad.

**`src/svg.rs`**
- `svg_roundtrip_preserves_segments_full_float_range`: Round-trip property: writing a path with `to_svg` and parsing it back with `from_svg` must preserve the path's segments exactly. This supplements `test_serialize_deserialize` above, which draws coordinates only from `[0, 1)` and never generates `ClosePath` or mid-path `MoveTo` elements. Coordinates here cover the whole finite `f64` range (Rust's float `Display` output round-trips exactly, and the SVG number lexer accepts plain decimal notation), and paths can close and restart subpaths.
- `from_svg_never_panics`: `from_svg` is documented as "try to parse", returning a `Result`; it must never panic, even on garbage input. The second generator branch draws from the SVG path character set so that near-miss inputs (commands with too few arguments, stray signs and dots, etc.) are actually reached rather than being rejected at the first byte.
- `arc_from_svg_arc_never_panics`: `Arc::from_svg_arc` accepts any `SvgArc` (in `from_svg` it is fed directly from parsed path data, which can contain arbitrary numbers) and must not panic; its only documented escape hatch is returning `None` for straight lines. The magnitude tiers deliberately probe the underflow/overflow regions where geometry code tends to collapse to 0 or NaN: nearly coincident endpoints (products of tiny differences square to zero) as well as the full finite range.
- `arc_from_svg_arc_underflow_breaks_internal_assertion`: KNOWN FAILURE — real bug, kept failing deliberately; do not "fix" the test. `Arc::from_svg_arc` guards only against `is_straight_line()` (radii smaller than 1e-5 or exactly coincident endpoints) before asserting `sum_of_sq != 0.0`. For endpoints that are distinct but closer than roughly 3e-162 (relative to the radii), `rx * p.y` and `ry * p.x` both underflow to zero when squared, so the assertion fails: a panic in debug builds. In release builds the subsequent division by `sum_of_sq == 0` produces an infinite/NaN arc center instead of a finite arc. Example: `from = (1e-170, 0)`, `to = (0, 0)`, `radii = (1, 1)`. Every case generated here is in the underflow family, so the test fails deterministically on every run.
