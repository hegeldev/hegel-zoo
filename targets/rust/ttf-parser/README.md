# ttf-parser

[harfbuzz/ttf-parser](https://github.com/harfbuzz/ttf-parser).

## What is tested

**`tests/tables/main.rs`**
- `tag_to_bytes_from_bytes_roundtrip`: ------------------------------------------------------------------ Property: Tag byte conversion round-trips. Evidence: `Tag::from_bytes`/`Tag::to_bytes` are inverse bit packings (lib.rs), and the `Tag::from_bytes` doc example. ------------------------------------------------------------------
- `face_parse_never_panics_on_arbitrary_bytes`: ------------------------------------------------------------------ Property: `Face::parse` and `fonts_in_collection` never panic on arbitrary bytes, and a successfully parsed face can be fully queried without panicking. Evidence: the crate advertises itself as a "safe" font parser, the AFL fuzz targets in testing-tools/ttf-fuzz assume exactly this, and the hand-written tests above check specific malformed headers. ------------------------------------------------------------------
- `face_parse_never_panics_on_font_shaped_bytes`: ------------------------------------------------------------------ Property: `Face::parse` never panics on structurally font-shaped garbage (valid magic + generated table directory), and a successfully parsed face can be fully queried without panicking. Evidence: same as the arbitrary-bytes property; this generator goes beyond the repo's AFL targets by always presenting a plausible directory, so table parsers actually see the garbage payloads. ------------------------------------------------------------------
- `face_never_panics_on_mutated_test_fonts`: (no doc comment)
- `regular_font_with_nonzero_index_is_out_of_bounds`: ------------------------------------------------------------------ Property: parsing a regular (non-collection) font with any non-zero index fails with FaceIndexOutOfBounds. Evidence: RawFace::parse treats a regular font "as a one-element collection" (lib.rs), and the `font_index_overflow_on_regular_font` unit test above pins index == 1; this generalizes it to all indices. ------------------------------------------------------------------
- `font_collection_index_contract`: (no doc comment)
- `glyph_index_never_returns_glyph_zero`: ------------------------------------------------------------------ KNOWN FAILURE. Property: `glyph_index` and `glyph_variation_index` never return GlyphId(0). Evidence: both are documented as "Returns `None` instead of `0` when glyph is not found", and cmap formats 0/2 plus format 4's glyph-array branch contain explicit glyph-is-zero checks showing the authors enforce this. This test FAILS on the pristine demo.ttf: `glyph_index('\u{FFFF}')` returns Some(GlyphId(0)). The format 4 `id_range_offset == 0` branch (src/tables/cmap/format4.rs) computes `code_point.wrapping_add(id_delta)` and returns it without the `glyph == 0` check that the sibling glyph-array branch has, so the standard end-of-table sentinel segment (start == end == 0xFFFF, idDelta == 1) maps U+FFFF to glyph 0. The `just(0xFFFF)` branch below makes the failure deterministic. ------------------------------------------------------------------
- `table_lookup_agrees_with_linear_directory_scan`: ------------------------------------------------------------------ Property: `RawFace::table` (binary search over the directory) agrees with a straightforward linear scan of `table_records`, both for tags that are present and for arbitrary tags. Evidence: `RawFace::table` docs ("Returns the raw data of a selected table") plus the record's own offset/length fields; the linear scan + slicing here is an independent oracle for the binary search + slicing in the library. ------------------------------------------------------------------
- `valid_font_queries_never_panic_full_ranges`: ------------------------------------------------------------------ Property: on pristine test fonts, every public accessor handles the full range of its argument types (glyph ids, chars, ppem, palettes, variation values including NaN/inf) without panicking. Evidence: generalizes all three AFL fuzz targets in testing-tools/ttf-fuzz, which only probe a handful of chars, in-range glyph ids, and a single variation value. ------------------------------------------------------------------
- `outline_glyph_bbox_encloses_emitted_points`: ------------------------------------------------------------------ Property: when `outline_glyph` returns a bounding box, every coordinate it emitted to the builder lies inside that box (within 1 font unit: `RectF::to_rect` truncates the f32 bbox toward zero), and the box is well-formed (min <= max). Evidence: `outline_glyph` docs ("Outlines a glyph and returns its tight bounding box"), and glyf/CFF builders extend the bbox with every emitted point, including Bezier control points. ------------------------------------------------------------------
- `set_variation_panics_on_non_finite_values_known_failure`: ------------------------------------------------------------------ KNOWN FAILURE: `Face::set_variation` panics in debug builds when the value is non-finite (NaN, +inf, -inf). `set_variation` places no documented restriction on `value`, but it feeds it straight into `VariationAxis::normalized_value` (src/tables/fvar.rs), which calls `parser::f32_bound`, whose `debug_assert!(val.is_finite())` (src/parser.rs:916) fires. Release builds silently produce a clamped/NaN-derived coordinate instead. This test is expected to FAIL (panic) on every run: the generator draws directly from the non-finite values that trigger the bug. Sibling properties exclude non-finite variation values so they keep testing everything else; see `exercise_face` and `outline_glyph_bbox_encloses_emitted_points`. ------------------------------------------------------------------
- `face_height_overflows_i16_known_failure`: ------------------------------------------------------------------ KNOWN FAILURE: `Face::height()` overflows i16 in debug builds. `height()` is `self.ascender() - self.descender()` (src/lib.rs:1599), a plain i16 subtraction. A successfully parsed face whose hhea says e.g. ascender = 16384, descender = -16385 (difference 32769) panics with "attempt to subtract with overflow" in debug builds and silently wraps to a negative height in release builds. `vertical_height()` (src/lib.rs:1705) has the same unchecked subtraction. Originally found by `face_parse_never_panics_on_font_shaped_bytes`. This test is expected to FAIL (panic) on every run: the drawn ranges guarantee the difference exceeds i16::MAX. Sibling properties skip `height()`/`vertical_height()` for such faces; see `exercise_face`. ------------------------------------------------------------------
