# csv

[BurntSushi/rust-csv](https://github.com/BurntSushi/rust-csv).

## What is tested

**`csv-core/src/reader.rs`**
- `hegel_chunked_input_equals_whole_input`: Property: parsing is independent of how the input is chunked — feeding `read_record` the whole input at once and feeding it the same bytes split at arbitrary boundaries yield the same records. This is the core streaming contract (`read_record` docs: the caller provides input as it becomes available and signals EOF with an empty buffer). One documented exception: `strip_utf8_bom` "will fail to strip off the BOM if only part of the BOM is buffered", so when the data starts with a UTF-8 BOM the first chunk is forced to be at least 3 bytes long.

**`csv-core/src/writer.rs`**
- `hegel_streaming_writes_equal_oneshot`: Property: writing the same records via the streaming API with tiny output buffers (resuming on `OutputFull`) produces byte-identical output to writing with one large buffer. The `field`/`delimiter`/ `terminator`/`finish` docs define this resumability contract. The chunk size is at least 2 because the writer emits some two-byte sequences atomically (escaped quotes, CRLF, the quoted empty record); with a 1-byte buffer those can never make progress, as documented on the `quote` free function.

**`src/byte_record.rs`**
- `hegel_byte_record_model`: (no doc comment)
- `hegel_trim_matches_documented_class`: Property: `ByteRecord::trim` removes exactly the whitespace bytes documented on the method (`[\t\n\v\f\r ]`) from both ends of every field. KNOWN BUG exclusion: fields containing `\v` (0x0B) are excluded here; the implementation uses `u8::is_ascii_whitespace`, which does not treat `\v` as whitespace, contradicting the documentation. That discrepancy is pinned by `hegel_trim_documented_class_known_bug`.
- `hegel_trim_documented_class_known_bug`: KNOWN FAILURE: pins a real (documentation) bug. `ByteRecord::trim` documents: "only bytes in the class `[\t\n\v\f\r ]` are trimmed", but the implementation trims via `u8::is_ascii_whitespace`, which does *not* include `\v` (0x0B). A field with a leading `\v` therefore keeps it. (Notably, the existing unit test `trim_whitespace_only` exercises `" \t\n\r\x0c"` — every documented byte except `\v`.)

**`src/reader.rs`**
- `hegel_dfa_nfa_equivalence`: Property: the DFA parser (default) and the NFA parser (`ReaderBuilder::nfa(true)`, exposed as a debug option) must produce identical record sequences, positions and errors for any configuration and any input. The csv-core unit tests check this for canned inputs via the `parses_to!` macro; this generalizes it.
- `hegel_nfa_corrupts_records_spanning_output_buffers_known_bug`: KNOWN FAILURE: pins a real bug. `csv_core::Reader::read_record_nfa` misuses `self.output_pos`: it both starts writing at `output[self.output_pos]` *and* returns a cumulative (not per-call) `nout`, while `read_record_dfa` always writes from offset 0 of the caller-provided buffer and returns per-call counts, adding `output_pos` only to the `ends` values. The `csv` crate's `read_byte_record_impl` advances the output window by `nout` between calls (the DFA convention), so on the NFA path every record whose unescaped data outgrows the current record buffer (`OutputFull` mid-record) has bytes written past their correct offsets and reads back corrupted. With a fresh `ByteRecord` (4-byte initial field buffer), any unterminated record of length >= 5 shows it: reading `aaaaa` with `nfa(true)` yields `aaaa\0`. Shrunk from `hegel_dfa_nfa_equivalence` (original counterexample: input [1,1,1,1,1], DFA [[1,1,1,1,1]] vs NFA [[1,1,1,1,0]]). The same corruption also triggers via `OutputEndsFull` resumes (found by the 10x exploratory run: delimiter-heavy records overflow the ends buffer mid-record with `output_pos > 0`), and would also trigger for records spanning multiple `fill_buf` chunks.
- `hegel_trailing_comment_line_yields_phantom_record_known_bug`: KNOWN FAILURE: pins a real bug. When the input ends inside a comment line (i.e. the final line starts with the comment byte and has no trailing terminator), the default DFA path emits a phantom empty record, while the NFA path (and the documented behavior of comments: such lines are skipped) yields nothing. Root cause: `transition_final_dfa` in csv-core emits a record for *any* non-start, non-final state at EOF, including `InComment`, whereas `transition_final_nfa` correctly maps `InComment` to `End`. Found by `hegel_dfa_nfa_equivalence` (shrunk counterexample: delimiter=0, comment=Some(0), input [0] => DFA [[""]], NFA []). Reproduces with a plain config: reading `"a,b\n# trailing comment"` with `comment(Some(b'#'))` yields [["a", "b"], [""]].
- `hegel_dfa_nfa_disagree_on_comments_with_any_terminator_known_bug`: KNOWN FAILURE: pins a real bug. The NFA exits the `InComment` state on a literal `\n` regardless of the configured terminator (`transition_nfa` hardcodes `b'\n' == c`), but when the terminator is `Terminator::Any(t)` the DFA's byte equivalence classes do not distinguish `\n` (`build_dfa` only adds `\r`/`\n` as classes for CRLF terminators). All bytes in the same class share one transition-table cell, so on the DFA path a comment never ends at `\n`: the rest of the input is swallowed as comment, and EOF inside the comment then emits the phantom empty record (see `hegel_trailing_comment_line_yields_phantom_record_known_bug`). Found by `hegel_dfa_nfa_equivalence` (shrunk counterexample: terminator=Any(0), comment=Some(127), input [127, 10] => DFA [[""]], NFA []). This test states the violated property directly: DFA and NFA must agree.
- `hegel_nfa_does_not_track_line_numbers_known_bug`: KNOWN FAILURE: pins a real bug. The NFA code paths in csv-core (`read_record_nfa`, `read_field_nfa`) never update `self.line`, while the DFA paths increment it on every `\n` consumed. With `nfa(true)`, every position reported by the reader claims line 1. Found by `hegel_dfa_nfa_equivalence` (position comparison).
- `hegel_position_seek_roundtrip`: Property: `position()` before reading a record can be `seek`ed to and yields the same record and all subsequent records again (documented on `Reader::position`: "seeking to a position returned here on the same data will result in parsing the same subsequent record").
- `hegel_flexible_vs_strict_record_lengths`: Property: with `flexible(true)` the reader returns records of varying lengths as-is; with the default strict mode, each record whose length differs from the *first* record's length yields an `UnequalLengths` error carrying the documented `expected_len`/`len` values (see `ReaderBuilder::flexible` and `ReaderState::add_record`).
- `hegel_reader_never_panics_on_arbitrary_input`: Property: the reader never panics on arbitrary input bytes under any configuration (including `trim` and header handling, and the `StringRecord` path which performs UTF-8 validation); byte positions never decrease and never exceed the input length; and the reader reports `is_done()` after exhaustion.

**`src/string_record.rs`**
- `hegel_trim_rebuilds_fields_and_preserves_position`: Property: `StringRecord::trim` is equivalent to rebuilding the record from the per-field `str::trim` results (the docs say it trims each field with the Unicode definition of whitespace), it preserves the record's position, and it is idempotent. Fields are full Unicode text, so exotic whitespace and multi-byte content exercise the internal bounds rebuild.

**`src/writer.rs`**
- `hegel_write_read_roundtrip_with_generated_config`: Property: writing records with any valid configuration and reading them back with the matching reader configuration yields the original records. Field data is arbitrary bytes (including delimiters, quotes, newlines and invalid UTF-8), which the writer must quote/escape as needed (see `Writer` docs: "Quote fields when necessary").
- `hegel_roundtrip_escape_byte_in_field_known_bug`: KNOWN FAILURE: pins a real bug. When `double_quote(false)` is set, the writer escapes *quotes* with the configured escape byte, but never escapes the escape byte itself (`csv_core::writer::quote` only searches for the quote byte). The writer knows such fields are dangerous — `WriterBuilder::build` in csv-core sets `requires_quotes[escape]` — but quoting cannot protect the data: the reader (with the matching `escape(Some(..))` config) interprets the escape byte inside a quoted field and takes the *next* byte literally. So a field consisting of just the escape byte is written as `"<esc>"` and read back as `<quote><terminator..>` garbage. Minimal counterexample (shrunk by hegel from the general round-trip property): delimiter=0, quote=1, escape=Some(29), field=[29] => encoded [1, 29, 1, 13, 10], read back as [[1, 13, 10]].
